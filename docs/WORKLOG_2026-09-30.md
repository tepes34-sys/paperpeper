## 1. paperpeper

### Distinguishing source data from reports

Automated checks use execution logs, databases, CSV files, and dashboards. Without accounting for when each source was produced, a healthy system can appear to have failed.

The work examined two kinds of check criteria:

- **The meaning of an update timestamp:** the generation time of aggregate statistics differs from the update time of an individual session. Before concluding that a dashboard has stopped updating, inspect the file's save time and the session content.
- **Source data and derived reports:** a manually generated CSV can lag behind the database. If a report lacks a row, compare it with the source database and the matching criteria first. Distinguish missing data from a report that has not been refreshed.

The principle is to **verify an observation tool's evidence before attributing its alert to trading logic**. The review procedure checks the timestamp and source of truth behind an alert before changing code.

### Temporary files and locks

The work also examined where temporary files are stored and how long they persist in recurring tasks. Files used only inside the execution environment are stored separately from files transferred to the device. Fixed transfer files can be refreshed on the next run, reducing incidental cleanup steps.

Locks require their own verification. Successful sequential reuse does not establish that two processes cannot enter concurrently. Tests must separately cover acquisition, simultaneous attempts, process interruption, and recovery on the next run.

### Next verification questions

- Is it clear which invocation or session each observation describes?
- Has lock contention been reproduced with two actual processes?
- Could an earlier price observation be applied incorrectly to a later state change?
- Are code, configuration, input period, and initial state recorded when comparing Main and Lab?

## 2. paperA

### Purpose of the Shadow Reliability Lab

paperA uses public market events to test the invariants, recovery, and portability of automated trading infrastructure. Market data provides realistic events; the system processing those events is the subject of verification.

The design separates strategy performance from operational reliability. Records affected by faults remain in operational analysis and the ledger, while being distinguished from samples used for fair strategy comparisons. Calculating performance from clean data and recovering missing data are separate tasks.

### Reproducible inputs

The work covered fixed fixtures and input hashes as a basis for reproducing results. The input contract is defined for the pure evaluator intended for later use, rather than creating a separate calculation solely for measurement.

Evaluation time, lookback range, data continuity, and evidence of no trading must be explicit for candidate frequency to be meaningful. Frequent candidates do not establish that actual entries, exits, or fair comparison samples will be sufficient. Measurement must be repeated after applying position holding periods and SKIP conditions.

Healthy inputs and fault inputs are also distinguished. Replaying a fixture without gaps does not exercise missing-data or recovery paths. Those paths need separate failure cases.

### Database and numeric rules

- **Experiment identity:** check design, strategy, currency, market, and schema versions before execution to prevent incompatible identities from being mixed.
- **Migrations:** apply changes in order and verify preservation of existing data and atomicity on failure.
- **Read-only behavior:** observe both database contents and the creation of surrounding files.
- **Numeric representation:** define boundaries that reject binary floating-point values for amounts and quantities, and round only at specified points.
- **Database type defenses:** verify that automatic storage type conversion cannot bypass the input contract.

Cost assumptions are separated from trading events. Changes to fee or slippage assumptions must not rewrite historical fill prices or the gross ledger. Net performance is presented with the assumption version used to calculate it.

### Collection and event capture

Real candles and interval status are stored separately. Missing data alone is not evidence that no trading occurred. An interval without sufficient evidence remains MISSING.

If a later observation differs from confirmed data, the difference is recorded as an event instead of overwriting the original. State changes and their explanatory Black Box events are preserved together. Reprocessing an event must not produce duplicate effects.

For short-lived execution, runs and cycles are distinct. Multiple process invocations for the same cycle must not duplicate the processing unit. OS locks prevent concurrent entry; database constraints and deterministic identifiers provide the final defense against duplicate state changes.

### The next verification boundaries

Pure strategies and position handling, ledger reconciliation, fault recovery, live data boundaries, and scheduled execution are separate verification stages. Fixture tests do not establish completed live operation. Results from one market do not establish that the same conditions hold in another market.

## 3. think

### Separating opinions, decisions, and invariants

think records design discussions across projects. GPT and Claude opinions are discussion material; implementation requirements are connected to approved decisions and project pull requests.

| Document | Role | Required evidence |
|---|---|---|
| Think | Discussion and proposals for one topic | Context, opinions, and open questions |
| Decision | A rule approved at a specific point in time | Approval, rationale, scope, and related pull requests |
| Invariant | An enduring condition verified repeatedly | A failure case and actual tests in each project |

A proposal does not become approved merely because it has been written down. The approver, approval date, and scope are recorded to distinguish discussion status from implementation status.

### Design topics considered

- **Time and data:** invocation time versus evaluation ticks, UTC storage versus session display, and candle confirmation criteria.
- **Gaps and prices:** evidence of no trading, KNOWN/UNKNOWN prices, and the actual price required at session end.
- **Recovery and quarantine:** historical exit replay versus new entries, effective time versus recorded time, and persistent marking of fault exposure.
- **Strategy contracts:** the boundary between candidates and A/B strategies, required inputs, and ENTRY/EXIT price conditions.
- **Operations and records:** Black Box events, alerts, explicit administrative actions, lock contention, and responses to recording failures.
- **Costs and precision:** the event ledger versus cost assumptions, cash constraints, Decimal arithmetic, and rounding points.
- **State transitions:** separate axes for operating mode, position state, and data integrity.

These topics make different data requirements and permitted actions explicit, including cases where similar terminology could otherwise obscure a different contract.

### Tracking revised decisions and implementation

When a new decision changes part of an earlier document, it identifies the provisions being superseded and preserves the earlier record. A canonical source is designated for the connections between discussions, decisions, and pull requests, so separate documents do not become contradictory implementation authorities.

Design approval and implementation completion are tracked separately. An approved decision does not establish that code, tests, and live operating verification are complete in every project.

### Transferring principles between projects

After reproducing and fixing a fault, the underlying principle is extracted into a Portable Improvement Note. The target project reproduces it independently with its own inputs and environment, then performs regression testing. Copying code alone does not verify a shared principle.

The process develops a one-off repair into reusable engineering knowledge:

**Failure → reproduction → fix → invariant candidate → PIN → independent reproduction in another environment → review**
