# 2026-09-30 — paperpeper · paperA · think

오늘 작업에서 다룬 설계와 검증 원리를 세 항목으로 정리합니다. 공개 문서는 운영 기록 원문과 비공개 저장소 참조 없이, 각 프로젝트의 목적·문제·해결 원리·다음 검증 질문을 설명합니다.

## 1. paperpeper

### 운영 점검에서 원본과 보고서 구분하기

자동 점검은 실행 로그·DB·CSV·대시보드를 함께 사용합니다. 각 자료가 언제 생성되는지 구분하지 않으면 정상 운영도 장애로 보일 수 있습니다.

이번 작업에서는 다음 두 유형의 점검 기준을 검토했습니다.

- **갱신 시각의 의미:** 전체 통계 생성 시각과 개별 세션 내용의 갱신 시각은 다릅니다. 하나의 날짜만으로 전체 대시보드가 멈췄다고 판단하기 전에 실제 파일 저장 시각과 세션 내용을 확인합니다.
- **원본과 파생 보고서:** 수동 생성 CSV는 DB의 최신 상태보다 뒤처질 수 있습니다. 보고서에 행이 없으면 원본 DB와 연결 기준을 먼저 대조하고, 데이터 누락과 보고서 미갱신을 구분합니다.

여기서 얻는 원리는 **관측 도구의 오류를 거래 로직의 오류로 오해하지 않는 것**입니다. 경고를 받았을 때 즉시 코드를 바꾸기보다 경고가 참조한 자료의 생성 시점과 정본을 확인하는 절차를 정리했습니다.

### 임시 파일과 잠금의 역할

반복 작업의 임시 파일 위치와 수명도 검토했습니다. 실행 환경 내부의 일시 파일과 장치로 전달되는 파일은 저장 위치를 구분합니다. 고정된 전달 파일은 다음 실행에서 갱신하도록 설계해 반복 작업의 부수적인 정리 단계를 줄입니다.

잠금은 별도 검증 대상입니다. 순차 재사용이 가능하다는 사실만으로 두 프로세스의 동시 진입이 안전하다고 결론 내릴 수 없습니다. 검증에서는 잠금 획득, 동시 시도, 프로세스 중단, 다음 실행의 복구를 각각 확인해야 합니다.

### 다음 검증 질문

- 관측값이 어느 실행·세션을 설명하는지 명확한가?
- 잠금 경합을 실제 두 프로세스로 재현했는가?
- 가격 기반 상태 변경에 과거 관측값이 잘못 적용될 여지가 있는가?
- Main과 Lab을 비교할 때 코드·설정·입력 기간·초기 상태를 기록했는가?

## 2. paperA

### Shadow Reliability Lab의 목적

paperA는 공개 시장 이벤트를 입력으로 자동매매 인프라의 불변식·복구력·이식성을 검증하는 실험실입니다. 시장 데이터는 현실적인 사건을 제공하고, 검증 대상은 사건을 처리하는 시스템입니다.

설계에서는 전략 성과와 운영 신뢰성을 분리합니다. 장애로 영향을 받은 기록은 지우지 않고 운영 분석과 장부에 보존하면서, 공정한 전략 비교의 표본에서는 구분합니다. 정상 데이터로 성과를 계산하는 것과 누락 데이터를 복구하는 것은 다른 작업입니다.

### 반복 검증 가능한 입력

고정 fixture와 입력 해시를 사용해 같은 입력으로 결과를 재현하는 흐름을 다뤘습니다. 측정 전용 계산을 별도로 만드는 대신 실제 사용할 순수 평가기의 입력 계약을 먼저 정의합니다.

평가 시각, lookback 범위, 데이터 연속성, 무체결 증거를 명시해야 후보 빈도에 의미가 생깁니다. 후보가 자주 발생한다는 사실은 실제 진입·청산이나 공정한 비교 표본이 충분하다는 뜻까지 포함하지 않습니다. 포지션 보유 시간과 SKIP 조건을 적용한 후 다시 측정해야 합니다.

정상 데이터만 있는 입력과 장애 입력도 구분합니다. 누락 없는 fixture를 잘 재생해도 누락·복구 경로가 검증되는 것은 아니므로, 별도의 실패 사례가 필요합니다.

### DB와 숫자 규칙

- **실험 identity:** 설계·전략·통화·시장·schema 버전이 섞이지 않도록 실행 전에 검사합니다.
- **migration:** 변경은 순서대로 적용하고, 기존 데이터 보존과 실패 시 원자성을 확인합니다.
- **읽기 전용:** DB 본문뿐 아니라 주변 파일 생성 여부도 관측합니다.
- **숫자 표현:** 금액과 수량에 binary float가 들어오지 않도록 경계를 정하고, 명시된 위치에서만 반올림합니다.
- **DB 형식 방어:** 저장소의 자동 형 변환이 입력 계약을 우회하지 않는지 확인합니다.

비용 가정은 거래 사건과 분리합니다. 수수료·슬리피지 가정이 바뀌더라도 과거 fill price나 gross 장부를 다시 쓰지 않는 것이 핵심입니다. net 성과는 가정 버전을 함께 표시합니다.

### 수집과 사건 기록

실제 candle과 interval 상태를 분리합니다. 데이터가 없다는 사실만으로 무체결을 확정하지 않으며, 증거 없는 상태는 MISSING으로 보존합니다.

한 번 확정한 데이터와 이후 관측이 달라지면 원본을 덮어쓰는 대신 차이를 사건으로 기록합니다. 상태 변경과 이를 설명하는 Black Box 사건은 함께 보존하고, 이벤트의 재처리는 중복 결과를 만들지 않도록 설계합니다.

단발 실행에서는 run과 cycle을 구분합니다. 같은 cycle에서 프로세스가 여러 번 실행돼도 처리 단위는 중복 집계되지 않아야 합니다. OS 잠금이 동시 진입을 예방하고, DB 제약과 결정적 식별자가 중복 상태 변경의 최종 방어선을 맡습니다.

### 검증의 다음 경계

순수 전략과 포지션 처리, 장부 대조, 장애 복구, 실제 데이터 경계, 예약 실행은 각기 다른 검증 단계입니다. fixture 시험은 실제 운영 완료를 대신하지 않으며, 한 시장의 결과만으로 다른 시장에서도 같은 조건이 유지된다고 판단하지 않습니다.

## 3. think

### 의견·결정·불변식을 분리하기

think는 여러 프로젝트의 설계 대화를 기록하는 문서 계층입니다. GPT와 Claude의 의견은 논의 자료이고, 구현 근거는 승인된 결정과 프로젝트 PR로 연결합니다.

| 문서 | 역할 | 필요한 근거 |
|---|---|---|
| Think | 한 주제의 논의와 제안 | 배경, 의견, 남은 질문 |
| Decision | 승인 시점의 확정 규칙 | 승인, 이유, 영향 범위, 관련 PR |
| Invariant | 반복 검증된 장기 조건 | 깨지는 실패 사례, 프로젝트별 실제 테스트 |

의견이 제안으로 정리됐다고 자동 승인된 것은 아닙니다. 승인자와 승인일, 결정의 영향 범위를 남겨 논의 상태와 구현 상태를 구분합니다.

### 설계에서 다룬 주제

- **시간과 데이터:** 실행 시각과 판단 tick, UTC 저장과 세션 표시, candle 확정 기준.
- **누락과 가격:** 무체결 증거, KNOWN/UNKNOWN 가격, 세션 종료에 필요한 실제 가격.
- **복구와 격리:** 과거 exit replay와 신규 진입의 분리, 사건 발생 시각과 기록 시각, 장애 영향의 지속 표기.
- **전략 계약:** candidate와 A/B 전략의 경계, 필요한 입력, ENTRY와 EXIT의 가격 조건.
- **운영과 기록:** Black Box, alert, 명시적 관리 조치, 잠금 경합과 기록 실패 시 대응.
- **비용과 정밀도:** 사건 장부와 비용 가정, 현금 제약, Decimal 연산과 반올림 위치.
- **상태 전이:** 운영 모드, 포지션 상태, 데이터 무결성을 별도 축으로 관리.

이는 기능 목록을 늘리기 위한 분류가 아닙니다. 같은 단어를 쓰더라도 데이터 요구 조건과 실행 가능 범위가 다르다는 점을 드러내기 위한 설계 기록입니다.

### 바뀐 결정과 구현을 추적하기

새 결정이 이전 문서의 일부 조항을 바꿀 때는 대체 범위를 명시하고 과거 기록을 보존합니다. 논의·결정·PR 연결에는 정본을 정해 서로 다른 문서가 상반된 구현 근거가 되지 않도록 합니다.

설계 확정과 구현 완료도 별도로 관리합니다. 결정이 승인됐더라도 각 프로젝트의 코드와 테스트, 실제 운영 검증이 모두 끝났다는 의미는 아닙니다.

### 다른 프로젝트로 옮기는 절차

장애를 재현하고 고친 다음 원리를 추출해 Portable Improvement Note로 전달합니다. 대상 프로젝트는 자신의 입력과 환경에서 독립 재현하고 회귀 검증을 진행합니다. 코드 복사 자체를 공통 원리의 검증으로 보지 않습니다.

**장애 → 재현 → 수정 → 불변식 후보 → PIN → 다른 환경의 독립 재현 → 검토**라는 흐름으로 일회성 수리에서 재사용 가능한 지식으로 발전시킵니다.
